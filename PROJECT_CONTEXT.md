# Project Context — Football Auction Manager

## Project purpose

Build a reliable desktop application for the real Calgary Vipers 2026 football player auction, then polish it into an internship portfolio project. ChatGPT Work maintains requirements, architecture, review, testing guidance, and documentation. Claude Code may continue implementation directly in this repository. The code must remain understandable and should grow milestone by milestone without unnecessary complexity.

## Technology and architecture

- Python desktop application
- CustomTkinter for the later GUI
- Pillow for player images
- JSON persistence during Phase 1
- pytest for automated tests
- Domain models are independent from the UI
- `services/` contains configuration loading, auction-queue randomization, player/team loading + search/filter + setup validation, team-roster resolution/summaries, SOLD/UNSOLD auction transaction logic (with re-auction rounds, the one-GK-per-team rule, and blocked-state detection), the shared in-memory `AuctionSession` (now with MOCK/LIVE mode and autosave), (Milestone 9) `services/persistence_service.py` for save/load/list/delete of JSON session snapshots under `saves/`, (September 2026) `services/auction_history_service.py` for read-only filter/sort/summary of the existing transaction history, (September 2026) `services/report_service.py` for read-only auction/team/price/FPL/OVR/re-auction analytics, (September 2026) `services/preferences_service.py` for organizer app preferences (fullscreen/display, SOLD/UNSOLD confirmation toggles) under `config/` — entirely separate from auction session saves, and (September 2026) `services/live_bid_service.py` (thread-safe live-bid validation, separate from the SOLD/UNSOLD transaction layer), `services/captain_bidding_server.py` (the local FastAPI/uvicorn phone-bidding server), and `services/captain_auth_service.py` (Phase 2: per-team PIN storage, session tokens, one-device-per-team enforcement, heartbeat connection tracking) — see "Captain Phone Bidding — Phase 1 — September 2026" and "Captain Phone Bidding — Phase 2 — September 2026" below
- `ui/` has a working CustomTkinter app shell (`main_window.py`, `theme.py`, `widgets.py`), the shared premium card-art system (September 2026) `player_card_art.py` (reused by both the Player Cards gallery and the Live Auction current-player card), and seven real data-driven screens (`ui/screens/live_auction_screen.py`, `ui/screens/player_cards_screen.py`, `ui/screens/players_setup_screen.py`, `ui/screens/teams_screen.py`, `ui/screens/auction_history_screen.py`, `ui/screens/reports_screen.py`, `ui/screens/settings_screen.py`) — every sidebar route now has a real screen; `assets/` holds the official branding logo, all 32 real player photos under `assets/players/`, and (September 2026) the standalone captain-phone web page `assets/captain_bidding/phone.html`

## Tournament rules

- Total players: 32
- Teams: 4
- Captains: 4, pre-assigned at zero cost
- Auction-eligible players: 28
- Starting auction budget: 100M per team (400M total)
- Final squad target/maximum: 8 players per team
- Each initial roster contains one captain; each team can buy at most 7 players
- A sale must never make a budget negative or produce a roster larger than 8
- A player cannot be sold twice (SOLD is permanent)
- Captains never receive a base price, sale price, auction sequence, SOLD, or UNSOLD result
- **UNSOLD is never permanent** (Milestone 8.1): a player marked UNSOLD returns in the next re-auction round — a fresh, reshuffled pool of every still-unsold auction-eligible player — and keeps returning in subsequent rounds until sold or until no team can legally take them. The auction is complete only when every auction-eligible player has been SOLD, not merely when one pass through a queue ends.
- **Each team may have at most one goalkeeper** (Milestone 8.1), counting the captain if the captain is a GK. A team that already has a GK cannot buy another. Each final squad is intended to contain exactly one GK; the canonical data (4 auction-eligible GKs, 0 captain GKs, 4 teams) satisfies this exactly.
- **A team at 8/8 players is no longer eligible to buy** (already true from Milestone 7's roster-size check; Milestone 8.1 additionally reflects it proactively in the UI and in re-auction eligibility).
- **A blocked auction state is detected, not looped forever** (Milestone 8.1): if no remaining unsold player can legally go to any team (e.g. every non-full team already has a GK, or every team is full), the auction reports BLOCKED with a readable message instead of endlessly reshuffling.
- **Base price depends on position** (First Auction Rules V2, supersedes the flat 1M minimum below): a goalkeeper's minimum legal price is 4M; every other position's is 2M. See `GK_BASE_PRICE`/`OUTFIELD_BASE_PRICE` in `models/player.py`.
- **A team must always retain enough budget to complete its remaining mandatory roster slots at their own minimum prices** (First Auction Rules V2's dynamic completion reserve, replacing the old flat-1M-per-slot pre-Milestone-9 rule): a sale is only legal if the team's budget after paying for it still covers every roster slot still needed afterward — the mandatory goalkeeper slot (if not yet owned and not being bought right now) at 4M, every other still-needed slot at 2M. A team may legitimately finish the first auction with 0M remaining. See "FIRST AUCTION RULES V2" below for the formula, worked examples, and enforcement details (supersedes "PRE-M9 BUDGET RESERVE RULE" further down, kept for history).

## Completed in Milestone 3

- `services/randomization_service.py`: `create_auction_queue(players, seed=None, expected_count=28)` builds one randomized queue of auction-eligible player ids
- Filters strictly on `auction_eligible`; independently re-verifies no captain slipped into that pool (defense-in-depth against a corrupted in-memory `Player`, since `is_captain`/`auction_eligible` are plain mutable dataclass fields, not enforced continuously)
- Rejects duplicate ids in the input collection, and rejects an eligible-player count that does not match `expected_count` (default 28, matching `settings.json`'s `auction_player_count`); `expected_count=None` skips that check for non-standard tournament sizes
- Uses a local `random.Random(seed)` instance (never the global `random` module) so the same players + seed always reproduce the same order, while omitting the seed uses ordinary randomness; the seed is stored on `Auction.random_seed` purely for reproducibility/debugging and is never required by tournament-mode UI
- `create_auction(players, seed=None)` wraps queue creation and returns a ready `Auction` with `status=IN_PROGRESS`, `current_queue_position=0`
- Never mutates the input player collection or touches `data/players.json` — the queue is a freshly built list of ids
- Extended the existing `Auction` model (not redesigned): added `is_initialized` (queue non-empty), `has_current_player` (a player is currently waiting), and `advance()` (moves `current_queue_position` forward one step, raising `ValueError` on an empty or already-completed queue instead of silently continuing)
- The queue is generated once per auction; nothing re-shuffles or re-samples from the full player database after a player is processed — `advance()` only ever moves forward through the queue that was built at auction start

## Completed in Milestone 8.1

A full manual mock auction (28 players, some intentionally left unsold) exposed that "28 attempts finished" was being treated as "auction complete" even with players still unsold — incorrect for the real tournament. This milestone corrects that and adds two tournament rules that hadn't been enforced yet (at-most-one-GK-per-team, full-team eligibility reflected proactively) plus detection for auctions that become impossible to finish.

- **Re-auction rounds** (`models/auction.py` + `services/auction_service.py`): `Auction` gained `round_number` (starts at 1) and `start_new_round(new_queue)`, which replaces the current (exhausted) round's queue with a freshly shuffled pool and resets `current_queue_position` to 0 — the shuffle itself still lives in the service, not the model, matching the existing "randomization is a service concern" decision. `AuctionStatus` gained `BLOCKED` alongside the existing `NOT_STARTED`/`IN_PROGRESS`/`COMPLETE`.
- **SOLD is the only permanent outcome now.** `sold_player_ids(auction)` (SOLD entries only) replaced `resolved_player_ids(auction)` (all entries, SOLD or UNSOLD — kept, but no longer used for this check) as the "cannot be auctioned again" test inside `_validate_current_player`. `eligible_for_reauction(auction, players)` is every auction-eligible player not yet in `sold_player_ids` — exactly the next round's pool, computed fresh at each round boundary rather than tracked incrementally.
- **Round transition logic** lives in a rewritten `_finish_transaction(auction, players, teams)`, called by both `process_sale` and `process_unsold` after their own mutation succeeds: `advance()` the current round; if the round isn't exhausted, nothing else happens; if it is and `eligible_for_reauction` is empty, `status` becomes `COMPLETE`; if players remain, `team_can_bid_for_player` checks whether *any* pending player could go to *any* team — if yes, a new round starts (queue reshuffled with a seed derived from `random_seed + round_number` for reproducibility, or unseeded if the auction itself was unseeded); if no, `status` becomes `BLOCKED` instead of starting a round that could never resolve, so nothing loops forever. `TransactionResult` gained an `auction_status: AuctionStatus` field; `auction_complete` is now simply `auction_status == COMPLETE` rather than "the round's queue happened to run out."
- **One-goalkeeper-per-team rule**: `team_has_goalkeeper(team, players)` resolves a team's *entire* roster (captain included) to check for a `Position.GK`; `process_sale` rejects a GK sale to a team that already has one ("Team already has a goalkeeper."), checked after the existing budget/roster-space checks and before the duplicate-assignment check (reordered slightly from the original Milestone 7 order — "already assigned to a team" is the more fundamental integrity problem and now takes priority when both are somehow true at once). `team_can_bid_for_player(team, player, players)` combines the roster-space and GK checks into one boolean, ignoring price (the price isn't known ahead of a UI selection) — used by the UI to disable ineligible teams and by the blocked-state check; it does not replace `process_sale`'s own validation, which stays authoritative.
- **GK setup validation** (`services/player_service.validate_setup`): a new "Sufficient goalkeeper coverage" check compares the number of auction-eligible GKs against the number of teams whose captain is *not* already a GK (that team's GK slot is already filled). On the canonical data this is 4 vs 4 — an exact match — so the check passes; it uses `>=` rather than exact equality, since a genuine GK surplus is a runtime concern the BLOCKED-state detection above already covers, not something worth blocking setup over.
- **Live Auction UI**: the round label now reads "Round 1" or "Re-Auction Round N", and progress ("X resolved this round / Y remaining this round") is scoped to the *current round's* queue, not a running total across rounds (the underlying `AuctionSession.resolved_count`/`total_queue_length`/`remaining_count` properties were redefined to read `current_queue_position`/`len(queue)` — which are already round-scoped since `start_new_round` resets them — instead of the old `len(history)`, which grows across rounds and would otherwise show nonsensical numbers like "30 resolved" for a 28-player tournament). Each of the 4 team buttons is now `state="disabled"` (grey, unselectable, no command) whenever `team_can_bid_for_player` says no for the current player, with a "FULL" or "HAS GK" label explaining why; when the current player is a GK, every team button also shows "GK 0/1"/"GK 1/1". If the previously-selected team becomes ineligible before the organizer acts (e.g. it just filled up), the selection is cleared automatically on the next render. A new **AUCTION BLOCKED** view (red heading, the exact message "Re-auction cannot continue: no eligible team can purchase the remaining player(s).", sold-so-far count, and final team states) renders whenever `session.is_blocked` is true, with no SOLD/UNSOLD controls — mirroring the existing Not-Started/In-Progress/Complete state-machine pattern in `_render()`.
- **Completion view** now shows "Sold" and "Rounds" (how many re-auction passes it took) instead of "Sold"/"Unsold" — at true completion "Unsold" is always 0 by definition, so it wasn't a useful stat; "Rounds" is.
- Verified end-to-end with a scripted walkthrough matching this milestone's own example exactly: round 1 (28 players) with 2 deliberately left unsold → confirmed the app does **not** show Auction Complete, and Re-Auction Round 2 starts automatically with a 2-player queue containing only those two → sold one, marked the other unsold again → confirmed Round 3 starts with only that one remaining player → sold it → confirmed **only now** does AUCTION COMPLETE appear (28/28 sold, 3 rounds). Also verified, via screenshots, that a full team correctly shows "FULL" and is disabled, and that when a GK is up for auction, teams already holding a GK show "GK 1/1" and are disabled while a team with room and no GK shows "GK 0/1" and stays selectable. Separately confirmed at the service layer (bypassing the UI entirely) that attempting to sell a second GK to a team that already has one is rejected with "Team already has a goalkeeper." and changes nothing.

## PRE-M9 BUDGET RESERVE RULE

A full manual mock auction exposed a real tournament-business-logic bug: a team could spend so much on one purchase that it became mathematically impossible to fill its remaining roster slots afterward (e.g. a team needing 3 more players with only 3M left could still be offered — and could still accept — a 2M or 3M purchase, leaving too little for the other 1-2 slots at the 1M minimum). This is a focused fix for that gap, completed before Milestone 9 (persistence/autosave) begins. Not a numbered milestone — no auction rules, ratings, positions, team data, GK rules, full-team rules, blocked-state semantics, player photos, or persistence status were otherwise touched.

- **Minimum legal price**: `MINIMUM_LEGAL_PRICE = 1` (1M), defined once in `models/team.py` and imported everywhere else that needs it (`services/auction_service.py`) rather than repeated as a magic number. `process_sale`'s existing price validation (`sale_price` must be a positive integer) already enforced this threshold before this fix; the fix only makes the constant explicit and shared rather than changing that check's behavior.
- **The reserve rule**: for any potential purchase, `remaining_slots_after_purchase = (max_squad_size - roster_size) - 1`, and `required_reserve_after_purchase = remaining_slots_after_purchase * MINIMUM_LEGAL_PRICE`. A sale is legal only if `budget_after_purchase >= required_reserve_after_purchase` — equivalently, `price <= current_budget - required_reserve_after_purchase`.
- **`Team.maximum_legal_bid`** (`models/team.py`, a property computed purely from the team's own `roster_size`/`max_squad_size`/`remaining_budget` — no `Player` data needed) implements that formula directly: the most a team could legally pay for its very next purchase while still able to afford every purchase after that at the minimum legal price. Worked examples (all verified by `tests/test_budget_reserve_rule.py`): fresh team (1/8, 100M) → max first-purchase price 94M (reserving 6M for the 6 slots still needed after that purchase); roster 5/8 with 3M left → max 1M; roster 6/8 with 5M left → max 4M; roster 7/8 (last slot) with 10M left → max 10M, since no reserve is needed after the final purchase.
- **`Team.can_afford_while_preserving_roster_budget(price)`** combines the minimum-price and maximum-legal-bid checks into one boolean, and **`Team.can_buy_player()`** (the model's own existing low-level invariant, already checked by `Team.add_purchased_player()`) now calls it alongside its prior checks — so even a caller that bypassed the service layer's own validation would still be rejected at the model layer. `Team.can_afford()` (the older, simpler "non-negative and within remaining_budget" check) is unchanged and still used elsewhere; the new check is strictly stronger (`maximum_legal_bid <= remaining_budget` always), not a replacement.
- **Service-layer enforcement** (`services/auction_service.py`, before mutation, same "validate everything, then mutate" pattern as every other `process_sale` check): the previous plain `price > team.remaining_budget` check was replaced with `price > team.maximum_legal_bid`, raising a new `budget_reserve_violation_message(team)` — a single shared helper (not duplicated between the service layer and the UI) that names the team, the reserve amount, the number of roster spots it's for, and the resulting maximum legal price (e.g. "Blackout FC must reserve 2M of its remaining budget for its 2 remaining roster spots. Maximum legal price is 1M."), or the simpler "Team does not have enough budget." once no further reserve is needed (the team's very last slot). A rejected sale remains fully atomic — the check runs before any mutation, exactly like the existing GK/roster-full/duplicate-assignment checks it sits alongside.
- **Team eligibility** (`team_can_bid_for_player`, reused unchanged by the UI's team-button disabling and by blocked-state detection — one helper, not duplicated): now also returns `False` when `team.maximum_legal_bid < MINIMUM_LEGAL_PRICE`, i.e. when the team couldn't legally pay even the minimum price for *any* player without breaking its own reserve. This doesn't require knowing the actual price in advance (unlike a specific transaction attempt) since `maximum_legal_bid` depends only on the team's own state. Combined with the pre-existing roster-space and GK checks, a purchase must now satisfy all three independently — the budget rule doesn't override the GK rule and vice versa.
- **Blocked-state integration**: `_finish_transaction`'s "can any pending player legally go to any team" check already calls `team_can_bid_for_player` for every (player, team) pair, so it automatically inherited the new budget-affordability condition with no separate code path — a team that's technically not full and has no GK conflict but can't legally afford even the minimum price is now correctly excluded, and an auction that becomes budget-starved on all sides now reports BLOCKED instead of incorrectly starting an unwinnable re-auction round.
- **Live Auction UI** (`ui/screens/live_auction_screen.py`): each of the 4 team buttons now shows a compact "Max {N}M" line (clamped to 0 for display in a pathological negative case) alongside the existing budget/roster/slots lines, so the organizer can see the legal ceiling before entering a price. An ineligible team's reason label now distinguishes three cases instead of two: "FULL" (roster full), "HAS GK" (goalkeeper conflict for the current player), or "LOW BUDGET" (can't legally afford even the minimum price while preserving its reserve). Entering a price above `team.maximum_legal_bid` is rejected *before* the confirmation dialog even opens (chosen over disabling the SOLD button, consistent with the screen's existing pattern of catching usability-level problems — no team selected, invalid price format — before calling the service layer), showing the exact same `budget_reserve_violation_message` text the service layer would raise, so the wording can never drift between the two surfaces. The price is never silently clamped.
- Verified end-to-end via a scripted `python main.py` walkthrough matching the ticket's exact manual scenario: a team forced (synthetic setup) to 5/8 roster with 3M remaining showed "Max 1M" and rejected a 2M attempt with the reserve message *before* opening the confirmation dialog, with budget/roster fully unchanged afterward; a 1M sale then succeeded, recalculating to 2 slots / 2M / "Max 1M"; repeating this to the final slot left the team at exactly 8/8 with 0M remaining. Separately verified a 7/8-roster team with 10M remaining could legally spend all 10M on its final player.
- Persistence/autosave remains unimplemented and is still the next (unscoped) major milestone — nothing here writes to disk beyond the in-memory `Team`/`Auction` objects any other transaction already mutates.

## Milestone 9 — Persistence / Autosave / Recovery

Everything through the Pre-Milestone-9 budget reserve fix ran entirely in memory: closing the app, a crash, or a restart lost the whole running auction. This milestone adds a full JSON-based persistence layer so a MOCK or LIVE auction survives exactly across a restart, with autosave, atomic writes, and corrupt-save safety — without touching auction rules, ratings, positions, team names, GK rules, or the budget reserve rule.

- **MOCK vs LIVE sessions** (`services/auction_session_service.SessionMode`): every session is explicitly one or the other, stored in the save file as `session_mode`. MOCK is for practice — any number may exist side by side, freely created and deleted. LIVE is the one protected, real-tournament session — always saved to the single `saves/live/live_active.json` slot, never to a mocks file and vice versa (structurally guaranteed by `persistence_service.session_save_path`, which is the *only* thing that decides where a save goes and switches purely on `session.mode`, which never changes after a session is created).
- **Save directory** (`services/persistence_service.py`, alongside `data/` and `assets/` under the existing `ROOT_DIR` pattern from `services/config_service.py` — packaging-friendly, no reliance on the current working directory): `saves/mocks/<session_id>.json` per practice session, `saves/live/live_active.json` for the current tournament session, and `saves/live/live_archived_<id>.json` for a previous LIVE session preserved (never deleted) when a new one replaces it. `saves/` is git-ignored (real tournament data must never be committed) and created on demand — nothing pre-creates it.
- **Session snapshot content**: a save file is `{schema_version, session_id, session_mode, name, created_at, updated_at, players: [...], teams: [...], auction: {...}}`, reusing `Player.to_dict()`/`Team.to_dict()`/`Auction.to_dict()` (and their `from_dict()` counterparts) unchanged rather than inventing a second serialization format — a `Player`'s `auction_status`/`sold_price`/`sold_to` and a `Team`'s `roster`/`remaining_budget`/`auction_spending` already carry both the static tournament data *and* the live auction state together, so one snapshot of the current `players`/`teams` lists captures everything Milestone 9 asked for (tournament snapshot, team state, and SOLD/UNSOLD state) with no separate representation. `Auction.to_dict()` already carried `queue`, `current_queue_position`, `history`, `status`, `random_seed`, and `round_number` from earlier milestones — nothing there needed to change either.
- **Snapshot immutability**: loading a save only ever reconstructs `Player`/`Team` objects from the save file's own embedded JSON — it never re-reads `data/players.json`/`data/teams.json`. A later canonical data change (a rating fix, a new photo, an organizer roster edit) can therefore never retroactively alter an already-saved session; only a brand-new session (`AuctionSession.start()`, which does call `load_players()`/`load_teams()`) picks up the newest canonical data. Verified by dedicated tests that mutate a temp canonical-data fixture between saving an old mock and creating a new one.
- **Tournament-rule constants (minimum legal price, GK assumptions, squad size) are not duplicated into the snapshot** — they're fixed business logic implemented in code (`models/team.py`'s `MINIMUM_LEGAL_PRICE`, `services/auction_service.py`'s GK/eligibility checks), not per-session configuration, so a restored session is governed by whatever rules the *running app version* implements, exactly like `max_squad_size`/`starting_budget` already were via each `Team`'s own fields.
- **Schema version**: `persistence_service.SCHEMA_VERSION = 1`, required in every save file. Loading rejects (via `PersistenceError`, never a raw exception) a missing, non-integer, newer, or older schema version with a clear message — no migration logic exists yet, as instructed ("do not invent migrations").
- **Atomic writes** (`atomic_write_json`): serialize to a `<name>.json.tmp` file in the same directory, flush, `os.fsync`, close the handle, then `os.replace` it over the target — atomic on both POSIX and Windows for a same-directory rename, and the handle is fully closed (required on Windows) before the replace happens. If serialization itself fails partway (a bad value, a simulated fault), the exception propagates *before* `os.replace` ever runs, so a previously valid save is always left completely untouched — verified directly (write valid data, then force a failing write, then assert the original bytes are unchanged) and via `save_session` wrapping any `OSError`/`TypeError`/`ValueError` into `PersistenceError` without advancing `session.updated_at`.
- **Autosave triggers**: `AuctionSession` gained an injectable `autosave: Callable[[AuctionSession], None] | None` hook (wired once, by `ui/main_window.py`, to `persistence_service.autosave_hook`; left `None` — meaning no disk I/O at all — in every existing test fixture that builds a session directly, so none of the ~450 pre-Milestone-9 tests touch disk). `_trigger_autosave()` runs after `start()` (the "persist a new session immediately" requirement), and after every *successful* `sell_current_player()`/`mark_current_player_unsold()` — which automatically covers SOLD, UNSOLD, round transitions, BLOCKED, and COMPLETE, since all of those are just different outcomes already reflected in `session.auction`/`session.teams` by the time the call returns. A rejected transaction raises before `last_result` is even updated, so it never reaches the autosave call — both in-memory and persisted state are provably unchanged for a failed sale (`test_rejected_transaction_does_not_alter_persisted_save`).
- **Autosave failure never rolls back a transaction**: `_trigger_autosave()` deliberately catches any exception the hook raises (a broad `except Exception` at this one specific boundary, explained in its own docstring, is intentional here — the alternative would be letting a disk failure crash or silently corrupt an auction that has already legitimately succeeded in memory) and records it on `session.last_save_error` instead of propagating. The Live Auction screen surfaces this immediately and prominently as a red "SAVE FAILED" indicator — the price is never silently treated as saved when it isn't.
- **Restore path**: `persistence_service.load_session(path)` is the *one* way to go from a save file back to a ready `AuctionSession` — it validates the file's shape, schema version, and session mode; reconstructs `Player`/`Team`/`Auction` via their own `from_dict()` (reusing each model's own `__post_init__` invariant checks — valid positions, non-negative budgets, no duplicate roster/queue ids — instead of re-implementing any of that); then cross-validates ids that only make sense *between* those objects (every roster/queue/history player id resolves within the snapshot, every captain resolves to a player actually marked `is_captain`, every SOLD entry's team name resolves) — deliberately validated only against the snapshot's own embedded data, never against today's `data/players.json`. Any failure raises a single `PersistenceError` type with a readable message; a raw `OSError`/`JSONDecodeError`/`KeyError` never escapes. Because `AuctionSession`/`MainWindow` identity must stay stable across screens, `AuctionSession.adopt(other)` copies a freshly-restored session's data into the *existing* shared session object in place (deliberately not copying `autosave`, so the app's existing wiring survives a resume) rather than the UI trying to swap object references across every screen.
- **Live Auction session launcher** (`ui/screens/live_auction_screen.py`'s "not started" view, replacing the old plain "START AUCTION" button — `_on_start_auction_clicked` is kept as a stable internal alias for "start a new MOCK session," since dozens of pre-existing tests call it directly): "NEW MOCK AUCTION" / "NEW LIVE AUCTION" buttons, plus a scrollable "Saved Sessions" panel with a LIVE section (the current `live_active.json`'s metadata and a Resume button, or "No active LIVE auction yet.") and a MOCKS section (every saved mock, newest first, each with its own Resume/Delete). A corrupt save renders as a clearly labeled "SAVE CORRUPT / UNREADABLE" card with only a Delete action — the listing never crashes because one file is bad (`persistence_service.summarize_save_file` never raises). Clicking "NEW LIVE AUCTION" while a LIVE save already exists opens a confirmation dialog explaining the existing session will be *archived, not deleted*, before `persistence_service.archive_live_session()` runs and a fresh LIVE session starts — starting a new MOCK never touches LIVE at all, so no confirmation is needed there. Deleting a saved session (mock or a corrupt file of either mode) goes through the same confirmation-dialog pattern SOLD/UNSOLD already used.
- **Session-mode + save-status indicators**: once a session is active, a compact badge row (added to the in-progress/complete/blocked views alongside the existing progress row) shows "MOCK SESSION" (muted gray) or "LIVE SESSION" (solid red — deliberately unmistakable) plus "Autosaved `<time>`" / "Not yet saved" / "SAVE FAILED" (red) — small enough not to compete with the player card on a projector.
- **Blocked/complete/re-auction all resume correctly**: a restored session is a real, fully-reconstructed `AuctionSession` — the same object type `sell_current_player`/`mark_current_player_unsold`/the GK rule/the budget reserve rule/blocked-state detection already operate on — so nothing about the Live Auction or Teams screens needed to know a session was resumed rather than freshly started. Verified directly: a resumed session can process another SOLD, can process UNSOLD into a fresh re-auction round, still rejects a second GK to a team that already has one, and still enforces the budget reserve rule's `maximum_legal_bid` after resuming.
- **Tests**: `tests/test_persistence_service.py` (50 tests) covers save/load content fidelity (schema version, mode, players/teams/queue/position/round/history/budgets/rosters/spending/SOLD-ids/BLOCKED/COMPLETE), restored-session gameplay (another SOLD, UNSOLD/re-auction, GK rule, budget reserve rule), autosave triggers and atomicity (including a rejected transaction leaving the save untouched, and a simulated mid-write failure leaving the previous file byte-identical), corrupt/unsupported-schema handling (invalid JSON, wrong shape, bad model records, unresolvable cross-references, wrong schema version — each via `PersistenceError`, never a crash), multi-session management (separate mocks, mock-cannot-overwrite-live, independent deletion, live-save detection, a completed session still loading), canonical-data snapshot immutability, and a full end-to-end "sell some, mark one unsold, save, discard in-memory objects, reload, verify exact match, continue, sell again, reload again, verify again" recovery scenario. `tests/test_live_auction_screen.py` gained 12 more tests wiring the same behavior through the actual screen (launcher buttons, resume, delete-with-confirmation, the new-LIVE archive confirmation, mode/save-status badges, and the "autosave failure never blocks a successful transaction" policy).
- Full regression: `python -m pytest -v` — **463 passed, 2 skipped** (the same 2 pre-existing, unrelated Tk-environment skips from every prior milestone), 0 failed. No existing test began touching real disk: every fixture that builds an `AuctionSession` directly leaves `autosave` at its default `None`, and only `MainWindow` (real app usage) or a test's own explicit, `tmp_path`-isolated fixture wires the real hook.

What Phase 2 replaced: the open, unauthenticated team selector (`POST /api/select-team`, removed) is now PIN login (`POST /api/login`); `/api/state`'s `team_id` query param and full `teams` list (any browser could read any team's private data) are now token-authenticated `own_team` data only; the phone's "TEST MODE — NO TEAM AUTHENTICATION" banner is gone, replaced by real per-team PINs; and Settings' Connected Devices counter (an anonymous heartbeat count) is now a named per-team CONNECTED/DISCONNECTED list.

- **The organizer's laptop remains the sole authority.** A phone can only view state and submit a bid amount for its selected team; nothing a phone sends can mark SOLD/UNSOLD, advance the current player, change a team's roster/budget/history, or start/end a round. Only `LiveAuctionScreen`'s own SOLD/UNSOLD buttons (organizer-operated) ever call `services/auction_service.process_sale`/`process_unsold`.
- **One authoritative live-bid state, reused rather than duplicated.** `models/auction.py`'s `Auction` dataclass already had unused `current_bid: int | None` and `leading_team_id: int | None` fields (already round-tripped by `to_dict()`/`from_dict()`); Phase 1 is the first code to actually read and write them. There is no `phone_current_bid`/`desktop_current_bid` split — the phone API, the desktop bid buttons, and the SOLD pre-fill all read/write the same two fields on the same `Auction` instance.
- **New `services/live_bid_service.py`** owns all bid validation and mutation via `place_bid(auction, players, teams, team_id_or_name, bid_amount) -> BidResult`. It re-validates, in order: auction initialized; `AuctionStatus.IN_PROGRESS` (COMPLETE → "Auction is complete. Bidding closed.", BLOCKED → "Auction is blocked. Bidding unavailable."); a current player exists; the team resolves; `services.auction_service.team_can_bid_for_player` (roster space + one-GK-per-team rule, reused, not reimplemented); bid is a non-bool `int`; bid ≥ `Team.MINIMUM_LEGAL_PRICE` (1M); bid strictly exceeds the current highest (equal is rejected, never silently raised); bid ≤ `Team.maximum_legal_bid` (the existing budget-reserve ceiling — an over-max bid is rejected outright, never clamped down to the max). A single module-level `threading.Lock` wraps the entire validate-then-mutate sequence, so two near-simultaneous bids (phone + desktop, or two phones in a future phase) can never both "win" — whichever acquires the lock second re-validates against whatever the first just committed and is rejected if it no longer qualifies.
- **`AuctionSession.place_live_bid(team_id_or_name, bid_amount)`** (`services/auction_session_service.py`) is the single shared entry point both the desktop UI and every phone API call go through — it delegates to `live_bid_service.place_bid` and triggers the existing autosave on acceptance. New `AuctionSession.current_bid`/`leading_team` read-only properties expose the live state for rendering. No second sale/bid mechanism exists anywhere else.
- **Live-bid reset on advancement, not player-scoped carryover.** `services/auction_service._finish_transaction` (called by both `process_sale` and `process_unsold`, exactly once per transaction) now unconditionally clears `auction.current_bid`/`leading_team_id` before revealing the next player — a bid can never carry from Player A to Player B. This was inlined directly into `auction_service.py` rather than added as a `live_bid_service` helper, since `live_bid_service.py` already imports from `auction_service.py` and the reverse import would be circular.
- **Local server: `services/captain_bidding_server.py`**, FastAPI + uvicorn, run in a background `threading.Thread` (daemon, `server.install_signal_handlers` overridden to a no-op since only the main thread may install signal handlers) so it never blocks the CTk `mainloop`. Binds `0.0.0.0` on port 8765; the LAN IP shown to the organizer is auto-detected (`get_lan_ip()`, a UDP socket "connected" to `8.8.8.8:80` without ever sending a packet, reading back the OS-selected outbound local address, falling back to `127.0.0.1` on any `OSError`) — the LAN IP is never hardcoded, and no OS firewall rule is ever touched programmatically. `start()` is idempotent (repeated calls do not spawn a second thread); `stop()` sets `should_exit` and joins the thread with a timeout, and is safe to call repeatedly or before ever starting. `MainWindow` owns one `CaptainBiddingServer` instance and calls `.stop()` from a `WM_DELETE_WINDOW` handler so closing the app never leaves a zombie server thread.
- **API surface** (all under the running server): `GET /health`; `GET /api/state?team_id=` — the only state a phone needs (`no_active_session`, session mode MOCK/LIVE, `auction_status`, round, `bidding_enabled`, current player's name/position/OVR/FPL/photo URL, `current_bid`, `leading_team_name`, every team's budget/squad/max-legal-bid, and the requesting phone's `selected_team`) and nothing about save-file internals; `POST /api/select-team` (Phase 1 test-mode team selection, no auth); `POST /api/bid` (calls `AuctionSession.place_live_bid` — the exact same call the desktop makes); `GET /photos/{filename}` serves player photos from `assets/players/` only, rejecting any filename containing a path separator and re-validating the resolved path is still inside that directory before returning it (no arbitrary filesystem access); `GET /` serves the phone page itself. - **Live Auction screen integration**: a compact "CAPTAIN BIDDING: RUNNING (ip:port)" / "CAPTAIN BIDDING: OFF" status line next to the existing save-status badges; a prominent CURRENT BID / LEADING TEAM row (gold/green, large text, "—"/"—" before any bid) directly above the existing team-status row; a "PLACE BID — {TEAM}" row of +1M/+2M/+5M buttons so the organizer can bid on behalf of any team from the desktop through the identical `place_live_bid` call a phone makes (this is also today's practical fallback if only one physical phone is available, and the permanent fallback for a connectivity failure or verbal bid). The screen polls `AuctionSession` every 500ms via Tk's own `after(...)` (never touching Tk widgets from the server thread — the server thread only ever touches the plain-Python `Auction`/`Team` objects guarded by `live_bid_service`'s lock) and only re-renders when a cheap state snapshot actually changed, and never while a SOLD/UNSOLD confirmation dialog is open (detected by walking `winfo_children()` for a `CTkToplevel`).

## Captain Phone Bidding — Phase 2 — September 2026

**Mixed mode is the permanent product design, not a transitional state.** Any number of captain phones from 0 to 4 may be connected at once, each PIN-authenticated and locked to exactly one team; the organizer's laptop can always bid manually for any team — connected, disconnected, or never logged in — through the exact same shared bid service Phase 1 already built. Nothing here changes SOLD/UNSOLD, standings, tournament FPL scoring, or packages an EXE, per the ticket's explicit scope.

- **Manual desktop bidding is never disabled by a captain connecting.** `ui/screens/live_auction_screen.py`'s team-status buttons are enabled/disabled purely by the existing roster/GK/budget-reserve eligibility rules (`team_can_bid_for_player`) — a team's connection state is never consulted for that decision. A connected team's button additionally shows a plain "PHONE CONNECTED" text line (informational only, see `_build_team_status_row`); a disconnected or never-logged-in team's button looks and behaves exactly as it always has.
- **New `services/captain_auth_service.py`** owns everything Phase 1 didn't need: PIN generation/storage, session tokens, one-active-device-per-team enforcement, and heartbeat-based connection tracking. It is deliberately independent of `AuctionSession`/`Auction` — team identity and PINs are tournament-day setup, not live-bid state, and must exist and stay stable even before an auction session is started for the day (so an organizer can open Settings and read out PINs before pressing "New Live Auction").
- **PIN storage**: `config/captain_bidding.json` (gitignored, alongside `config/user_preferences.json`), atomic-write-then-`os.replace` (the same small pattern `services/preferences_service.py` already uses, duplicated rather than imported for the same reason preferences duplicated it from persistence). PINs are 4-digit strings generated with `secrets.choice` (not `random`), guaranteed unique across the 4 teams by regenerating the whole batch until no duplicate occurs. A missing or unreadable/malformed file (bad JSON, wrong shape, a non-4-digit value, a duplicate PIN) is recovered by generating and persisting a fresh, unique set immediately — this only happens once per actual problem, never on every launch, so restarting the app during tournament prep never silently changes a captain's PIN. PINs are never written into `data/players.json`, team canonical data, or auction history/saves.
- **PIN privacy is structural, not just a UI convention.** `CaptainAuthService.get_pins()`/`get_pin()` are called only from `ui/screens/settings_screen.py` — no route on `CaptainBiddingServer` ever calls them, so there is no way for any phone, authenticated or not, to retrieve any team's PIN over the network. A wrong PIN is always rejected with the same generic "Invalid PIN." message; it never reveals which team (if any) it belonged to.
- **Auth session design**: login (`CaptainAuthService.login(pin, remote_key=None)`) issues an opaque `secrets.token_urlsafe(24)` token mapped to exactly one team; the token is the browser's only credential from then on (sent as an `X-Captain-Token` header, never the raw PIN again). Tokens are intentionally **not persisted** — they live only in the running `CaptainAuthService` instance's memory. A `CaptainBiddingServer` STOP followed by another START does *not* lose them (the same `CaptainAuthService` instance keeps running underneath the HTTP layer the whole time — a nicer property than the ticket's "acceptable to re-login" bar); a full **application** restart does lose them (a fresh `CaptainAuthService` is constructed), so a captain simply re-enters their still-unchanged PIN.
- **AUTHENTICATED vs. CONNECTED are two different things, tracked separately.** AUTHENTICATED means a still-valid token exists for that team (survives a brief Wi-Fi drop — never auto-invalidated just because a heartbeat is late). CONNECTED means that token's owner has been seen (any `/api/state` poll or `/api/heartbeat` call counts) within the last 5 seconds. Settings shows three states per team: NOT CONNECTED (nobody has ever logged in, or was reset), CONNECTED (authenticated and recently seen), DISCONNECTED (authenticated but stale — e.g. Wi-Fi dropped) — a strict superset of the ticket's literal two-state example, giving the organizer a clearer diagnostic without extra complexity.
- **One active device per team, enforced at login, not by locking out the PIN.** `CaptainAuthService.login` rejects a second login for an already-authenticated team with `error_code="already_connected"` and a message naming the team (e.g. "Blackout FC is already connected. Ask the organizer to reset the connection.") — this check fires regardless of whether the existing session is currently CONNECTED or merely DISCONNECTED-but-still-authenticated, exactly covering the "captain changes phones" scenario the ticket's RESET CONNECTION control exists for.
- **Organizer reset (`CaptainAuthService.reset_team_session(team_id)`)** invalidates only that team's token — never PINs, roster, budget, history, or the live bid. A self-service `logout(token)` also exists (wired to the phone's own "Log out" link) for a captain to free their own slot without organizer involvement, and `/api/logout` on the server exposes it.
- **Regenerate All PINs (`CaptainAuthService.regenerate_pins()`)** generates and persists an entirely new, unique PIN set and clears every current session (every captain must re-enter their new PIN) — gated behind a confirmation dialog in Settings, matching the ticket's explicit "must require confirmation" and "invalidates existing captain logins" rules. It never touches an auction session, save file, or canonical player/team data (verified by a dedicated no-mutation test).
- **Basic local-LAN brute-force throttling**: after 5 consecutive failed PIN attempts from the same remote key (the caller's IP, when known), a 10-second lockout applies before another attempt from that key is processed — enough to rule out a trivial exhaustive 10,000-guess search over a 4-digit PIN without meaningfully inconveniencing a fumbling captain. A valid PIN from a *different* key is never affected by another key's lockout. This is explicitly local-tournament-appropriate hardening, not internet-banking-grade — matching the ticket's own framing.
- **Team identity for a bid comes only from the authenticated token, never the request body.** `services/captain_bidding_server.py`'s `BidRequest` pydantic model has no `team_id` field at all — even a payload with a forged `team_id` is structurally ignored, since the handler never reads it; `AuctionSession.place_live_bid` is always called with the team the token resolves to. Verified directly: a Darkstar-authenticated client sending `{"amount": 5, "team_id": <Blackout's id>}` still bids for Darkstar (`test_bid_payload_cannot_override_team_identity`).
- **API surface (Phase 2, replacing Phase 1's)**: `GET /health` (unchanged); `POST /api/login` (`{"pin"}` → token + team on success, generic rejection otherwise); `POST /api/logout`; `POST /api/heartbeat`; `GET /api/state` (token optional — returns public, projector-equivalent auction state — mode, status, current player, current bid, leading team — to anyone; adds `authenticated`/`team_id`/`team_name`/`own_team` only for a valid token; `session_invalid: true` distinguishes "your session was reset/regenerated/the app restarted" from "you never logged in," so the phone can show the right message); `POST /api/bid` (`{"amount"}` only, requires a valid token, 401 otherwise); `GET /photos/{filename}` and `GET /` (unchanged, still public/path-traversal-safe). `/api/select-team` no longer exists.
- **`CaptainBiddingServer`** now owns a public `self.auth: CaptainAuthService` — Settings and Live Auction call it directly, in-process (never over HTTP), for PIN display, `connection_overview()`, `connected_count()`, `reset_team_session()`, and `regenerate_pins()`. The old anonymous per-browser heartbeat (`touch_client`/`connected_device_count`/an arbitrary `client_id`) is gone, replaced entirely by the per-team, identity-based tracking above.
- **Settings screen — Phase 2 controls**, replacing Phase 1's: Server/LAN Address/Authentication rows now read "PIN ENABLED"; a full-width "CAPTAIN PINS / CONNECTIONS" list shows, per team, its PIN (with a COPY button), CONNECTED/DISCONNECTED/NOT CONNECTED status, and a RESET CONNECTION button; a REGENERATE ALL PINS button (confirmation-gated) sits below the list. A one-time banner appears if the PIN file had to be recovered from missing/corrupt state. START/STOP/COPY ADDRESS are otherwise unchanged from Phase 1.
- **Live Auction screen — Phase 2 additions**: the compact projector status line now reads "CAPTAIN BIDDING: RUNNING (ip:port)  N / 4 ACTIVE" (the live connected count) instead of just RUNNING/OFF; team-status buttons gain the optional "PHONE CONNECTED" line described above. No PIN is ever rendered on this screen, by construction (Settings is the only code path that ever calls `get_pins()`/`get_pin()`).
- **Phone page (`assets/captain_bidding/phone.html`)** was rewritten: the old open team-selector grid is gone, replaced by a 4-digit PIN entry screen (`inputmode="numeric"`, large tap-friendly input). A successful login shows "CONNECTED AS {TEAM}" with no further team choice possible from that browser; a "Log out" link calls `/api/logout` and returns to the PIN screen. The token is stored in `localStorage` (never the raw PIN) and sent as `X-Captain-Token` on every `/api/state`/`/api/bid` call. If a poll ever reports `authenticated: false` while a token is stored, the page shows "Your session was reset. Please enter your PIN again." (when `session_invalid` is true) and clears the stale token — this is what a captain sees after an organizer RESET CONNECTION, a PIN regeneration, or an app restart.
- **Reconnect behavior, exactly as documented for the ticket's three scenarios**: a browser refresh keeps the same `localStorage` token and stays logged in (no re-poll of `/api/login` needed). A brief Wi-Fi drop and reconnect resumes seamlessly — the token is still authenticated server-side (heartbeat merely lapses and resumes; see AUTHENTICATED vs. CONNECTED above), so the phone simply starts polling successfully again with no visible interruption beyond the CONNECTED pill briefly not updating. A `CaptainBiddingServer` STOP/START (not an app restart) also does not require re-login, since the same `CaptainAuthService` survives it — better than the ticket's "acceptable to re-enter PIN" bar. Only a full application restart forces every captain to re-enter their PIN (unchanged, since it's still valid).
- **Concurrency**: unchanged from Phase 1 — `services/live_bid_service.place_bid`'s single module-level lock remains the sole place `current_bid`/`leading_team_id` are mutated, regardless of how many authenticated captains or desktop clicks race to call it. Verified again at the HTTP layer with all four teams authenticated simultaneously and a `threading.Barrier`-synchronized pair of equal-value bids through the real API (`test_four_authenticated_teams_can_each_submit_a_bid`, `test_simultaneous_equal_bids_exactly_one_accepted_through_api`).
- **Persistence**: unchanged from Phase 1 for auction/bid state (still `Auction.current_bid`/`leading_team_id`, still autosaved on every accepted bid). Captain PIN configuration persists separately in `config/captain_bidding.json` (see PIN STORAGE above) — deliberately outside the auction session snapshot, since PINs are a tournament-day identity concern, not auction business data. Browser auth session tokens are never persisted at all (see AUTH SESSION DESIGN above); this was a deliberate choice, not an oversight, since persisting bearer tokens to disk would be a meaningfully bigger security surface for very little practical benefit at one-day-tournament scale.
- **QR code joining was intentionally skipped**, per the ticket's own explicit escape hatch ("if it complicates the ticket, skip and document as optional future improvement — do not delay Phase 2 for QR"). Documented here as optional future work: a generic QR encoding the LAN URL (captains still enter their own PIN after scanning) would need only a small `qrcode` dependency and a one-time image render in Settings — low risk, deliberately deferred rather than adding a dependency this ticket didn't require.
- **New tests**: `tests/test_captain_auth_service.py` (37 tests — PIN generation/uniqueness/format/persistence/reload, missing/corrupt/malformed/duplicate-PIN recovery, regenerate changing PINs and invalidating sessions without touching canonical data, valid/invalid login, PIN-not-leaked-on-failure, token creation/resolution/reuse, second-device-same-team rejection, organizer reset, 0-4 simultaneous authenticated teams, heartbeat/stale/reconnect connection-status transitions, logout, and rate-limiting). `tests/test_captain_bidding_server.py` was rewritten for the token-based API (39 tests — login/logout/heartbeat, own-team-only state data, no-PIN-leakage, the forged-`team_id` security test, 401/409/422/429 status mapping, photo/index serving, real-port lifecycle including auth-survives-restart, and HTTP-level concurrency). `tests/test_live_auction_screen.py` gained a "CAPTAIN PHONE BIDDING — PHASE 2" section (PHONE CONNECTED indicator shown/absent, projector active-count display, desktop bidding for a connected team, a disconnected team, and with zero phones connected, and one captain's disconnect never blocking another team or the desktop). `tests/test_settings_screen.py` gained PIN-management-UI coverage (PINs shown, per-team status, RESET CONNECTION, REGENERATE ALL PINS via the confirmation dialog's seam, no-mutation-of-auction-state, and Live-Auction-never-renders-a-PIN) consolidated into two real-`MainWindow` tests to avoid multiplying this file's already-documented multi-root Tk flakiness.

In source mode, the same repository root; in a packaged build, the directory containing `sys.executable` — i.e., beside the .exe, never inside `_internal/`. This is the fix for the ticket's core packaging hazard: bundling active writable state inside PyInstaller's read-only (and, for onefile, temporary) payload.
  - `services/config_service.py`'s `ROOT_DIR` is kept as a **backward-compatible alias for `RESOURCE_ROOT`** (every existing importer of `ROOT_DIR` across ~10 files reads canonical/bundled data, never writable state), so nothing outside the three writable-state modules below needed to change.

FastAPI/Starlette needed no dedicated hook (they use ordinary `import` statements PyInstaller's static analysis already follows). The spec's `hiddenimports=[]` was deliberately left empty and only the real build's actual runtime behavior was used to decide whether more were needed (per the ticket's "do not blindly add everything, use collection helpers only as needed") — none were.

Produces `dist/Calgary Vipers Auction 2026 RC0/Calgary Vipers Auction 2026.exe` — the **folder** is RC0-labeled so it can never collide with or be mistaken for a future `dist/Calgary Vipers Auction 2026/` final-release folder, while the **.exe itself** keeps the clean final-release filename `Calgary Vipers Auction 2026.exe` the ticket asked for. `console=` is controlled by the `CVA_DEBUG_CONSOLE` environment variable (unset/`0` → windowed, the user-facing RC0 build; `1` → a console-attached debug variant, built and used during this ticket's own verification to see startup output/tracebacks). ## Windows RC0 Packaged-Runtime Stabilization — September 2026

**This is a packaged-runtime debug/stabilization pass, not the final v1.0 release.** The organizer's real Windows laptop reported the packaged RC0 `.exe` behaving badly — slow, captains randomly flapping to DISCONNECTED, and critically, START CAPTAIN BIDDING never actually reaching RUNNING (Settings stuck showing Server: OFF / LAN Address: —). Per this ticket's own explicit instruction, nothing was guessed: every root cause below was reproduced with a real frozen `.exe` before any fix was written, and every fix was re-verified against a real frozen `.exe` afterward.

### ROOT CAUSE — server start failure / missing LAN address

**Found, not guessed, by reproducing against a real frozen executable with a controlled A/B comparison.** A diagnostic script built the same way as the real app (same dependency graph, same PyInstaller mechanics) constructed the real `MainWindow`, and:
- Calling `captain_bidding_server.start()` **immediately** after construction: RUNNING in ~60ms. Fine.
- Calling it **after navigating through several screens first** (Player Cards, Settings, Reports, Teams, Auction History, Live Auction — an entirely ordinary "explore the app, then open Settings" organizer workflow): the server thread stayed alive but **never** reached `uvicorn.Server.started = True`, confirmed by waiting a full 60 real seconds, not just this ticket's own timeout budget.

Reading uvicorn's own source (`uvicorn/loops/asyncio.py`) explained why: on Windows, uvicorn's default loop factory returns `asyncio.ProactorEventLoop` — built on Windows I/O Completion Ports. Something about running `ProactorEventLoop`'s own initialization on a background thread *after* the main thread had already done substantial CustomTkinter/PIL work left it unable to ever complete the server's async startup — the thread never crashed, never raised, it simply never finished. **Fix**: a small `services/captain_bidding_server._threaded_server_event_loop()` factory forces `asyncio.SelectorEventLoop` instead — uvicorn's own documented alternative (normally reached via its `use_subprocess` flag), which doesn't depend on IOCP. This server never uses subprocesses, pipes, or `add_reader` on anything but plain TCP sockets, so `SelectorEventLoop` has no functional gap here. Re-verified against the exact same frozen-executable reproduction (heavy screen-switching, then start): **RUNNING in ~50ms**, with a real `/health` request succeeding immediately. This single fix is the actual resolution for both the "START CAPTAIN BIDDING does not work" and "LAN Address remains —" symptoms — the LAN address row was only ever blank as a *consequence* of the server never reaching RUNNING (Settings only shows an address once `is_running` is true), not a separate bug in address detection itself.

A secondary, real bug was found and fixed along the way: uvicorn signals a bind failure (e.g., port already in use) by calling `sys.exit(STARTUP_FAILURE)` from inside the server thread — this raises `SystemExit`, a `BaseException`, which the *previous* code's plain `except Exception` around `server.run` never caught, so that failure mode also died silently. Both are now handled (see "SERVER LIFECYCLE FIX" below).

### ROOT CAUSE — UI slowness

Measured, not assumed (per this ticket's own "do not optimize blindly" instruction):
- **Settings recomputed its full diagnostics (canonical player/team reload, setup validation, a 32-file photo-existence disk scan) on every single `_render()`** — which fires on every preference toggle, PIN reset, and server start/stop click. Measured: ~1.05ms of pure I/O per render for this alone. Fixed by computing it once in `__init__` (already true for player/team/validation; the photo scan was the remaining gap) — now ~0.0002ms per render (cached attribute reads only).
- **Live Auction's 500ms poll re-renders whenever *anything* it tracks changes** — including, after this ticket's own fix, a captain-bidding server-state or connected-count change that has nothing to do with the current player — and a full re-render was unconditionally re-running the premium player-card PIL compositing (photo load + crop + paste), measured at ~35-40ms per call, even when the player hadn't changed. Fixed with a composited-image cache in `ui/player_card_art.py`, keyed by player + exact geometry. Measured before/after on a real render with the same player: **183ms → 121ms** (a real, direct ~62ms reduction attributable to this specific fix; the remainder is Tk/CustomTkinter widget-creation cost, an existing, deliberate "clear and rebuild" architecture shared by every screen in this app — restructuring that into incremental/partial updates would be a much larger UI-architecture change than this stabilization ticket's scope, and was not attempted).
- The **steady-state 500ms poll cost, when nothing has changed at all** (the overwhelmingly common case), was independently measured at ~0.004ms per tick — confirming the polling callback itself was already appropriately cheap even before this ticket; the cost only ever came from the (now-cheaper) `_render()` calls it occasionally triggers.
- No other per-poll filesystem/network work was found: PIN config, preferences, and canonical data are all read once, not on a poll cycle; LAN IP is only resolved when a caller actually asks for `lan_url` (Settings' own render, not the 500ms loop).

### ROOT CAUSE — random captain disconnects

Not a bug, an overly aggressive default: `services/captain_auth_service.py`'s `_ACTIVE_WINDOW_SECONDS` (a captain reads CONNECTED if seen within this window) was `5.0` — too tight for a mobile browser throttling its own timers when the screen dims or the tab isn't foreground, a moment of Wi-Fi latency, or the packaged app itself briefly stalling, any of which can silently push one 750ms poll past 5 seconds. Widened to `15.0` (within the ticket's requested 12-20s range). This was already architecturally separate from authentication (`is_connected` vs. `is_authenticated`) — a stale heartbeat has never invalidated a captain's login, and still doesn't; only the *displayed* CONNECTED/DISCONNECTED badge was flapping too eagerly.

### SERVER LIFECYCLE FIX

`services/captain_bidding_server.py` gained a real `ServerLifecycleState` enum (`OFF`, `STARTING`, `RUNNING`, `FAILED`, `STOPPING`) as a thread-safe property (`CaptainBiddingServer.state`, guarded by a lock separate from the auth service's own), plus `last_error: str | None`. `start()` is now **non-blocking**: it reserves a port (see below), spawns the server thread, spawns a short-lived background *watcher* thread, and returns almost immediately with `state == STARTING` — the caller (Settings) is never blocked waiting for a slow or failing bind, satisfying the ticket's explicit "click START → immediately show STARTING → UI remains responsive → transition to RUNNING or FAILED" requirement. The watcher thread confirms the transition to `RUNNING` (once `uvicorn.Server.started` is true) or `FAILED` (thread died, or an 8-second budget elapsed with neither) without ever touching a Tk widget itself — Settings discovers the result via a short-lived `after(200, ...)` poll scheduled only while STARTING, cancelled in a new `destroy()` override if the screen is torn down first. The server thread target (`_run_server`) now explicitly catches `SystemExit` (uvicorn's own bind-failure signal — see above) in addition to `Exception`, recording a clear `last_error` either way instead of dying silently. `stop()` is unchanged in shape (still a bounded, synchronous `join`) but now also drives the same state machine (`STOPPING` → `OFF`) and is safe to call from `FAILED` (clears the error, ready to retry) as well as `RUNNING`.

### LAN DETECTION FIX

`get_lan_ip()` now returns `str | None` — never the old fallback of `"127.0.0.1"`, which looked like a valid address but no phone could ever actually reach. Detection now tries two independent sources: the existing UDP-route trick, then (new) every address `socket.gethostbyname_ex(socket.gethostname())` resolves, so an environment where the UDP trick fails outright (no default route at all — some VPN/virtual-adapter configurations) still has a chance of finding an address. Loopback addresses are always filtered out of both sources. When multiple candidates exist, an RFC1918 private address (`10.x.x.x`, `172.16-31.x.x`, `192.168.x.x`) is preferred over anything else, so a phone-usable Wi-Fi/hotspot address is chosen over an unrelated virtual adapter. `CaptainBiddingServer.lan_url` is `None` when no address is found — deliberately independent of server `state`, per the ticket's explicit "server bind success and LAN detection success are separate concerns" requirement: Settings shows **Server: RUNNING** with **LAN Address: Unavailable — try http://localhost:\<port\> on this computer** rather than ever implying the server itself is down.

### PORT HANDLING

`CaptainBiddingServer._reserve_port` probes for an available port starting at the configured one (default 8765), trying up to 10 ports above it (`PORT_FALLBACK_RANGE`) via a quick bind-then-close check before handing the winner to uvicorn — addressing the plausible real-world case of a previous, not-fully-exited copy of the app still holding the port. If a fallback port is used, `actual_port`/`lan_url` reflect the real bound port, never the originally-configured one. If the entire range is exhausted, `state` becomes `FAILED` with a clear, specific message rather than an infinite silent OFF. This is a best-effort bind-probe (not airtight against a razor-thin TOCTOU race) — more than sufficient for a single organizer's laptop, not a hostile multi-tenant environment.

### DIAGNOSTIC LOG FILE

New `services/app_logging.py`: a small, bounded (`RotatingFileHandler`, ~2MB × 3 backups) log at `logs/calgary_vipers_auction.log` under `WRITABLE_ROOT` (beside the .exe when packaged) — the only way to see what happened in the final windowed (console-less) build without rebuilding a debug variant. Logs app startup (version, frozen state, resource/writable roots) and every captain-bidding lifecycle transition (START/STOP requested, selected port, RUNNING, FAILED + reason). Never logs a PIN or an auth token — verified directly with real generated PINs/tokens exercised through the real login/lifecycle code paths, not a static text search. `get_logger()` specifically checks for its own `RotatingFileHandler` type (not just "does this logger have any handler at all") before attaching — found necessary because another party attaching an unrelated handler to the same logger name first (discovered via this module's own test suite: pytest's log-capture plugin does exactly this) would otherwise silently skip attaching the real file handler at all.

### VERSION

`APP_VERSION` bumped `"0.9.0-rc0"` → `"0.9.0-rc1"`.

### Full regression and RC1 build

`python -m pytest -q` — **926 passed, 6 skipped, 0 failed**, confirmed across multiple full runs after every change in this ticket, including the event-loop fix (up from RC0's 898/6/0 baseline — net new passing tests from this ticket's additions, zero regressions). `build_windows.bat`/`calgary_vipers_auction.spec` now produce `dist/Calgary Vipers Auction 2026 RC1/Calgary Vipers Auction 2026.exe` without touching `dist/Calgary Vipers Auction 2026 RC0/` (both the build script's cleanup step and the spec's `DIST_FOLDER_NAME` are scoped to the current RC's own output folder specifically) — RC0 is kept alongside RC1 for comparison. The real RC1 `.exe` was re-verified against the exact frozen-executable reproduction that originally exposed the hang, confirming the fix.

### Known issues after this ticket

- Settings' `_render()` (a full clear-and-rebuild of its widget tree, ~327ms measured) is unchanged — this ticket fixed the *data* recomputation inside it, not the Tk widget-rebuild cost itself, which is a pre-existing, deliberate architectural pattern shared by every screen. It's a brief, one-off stutter on an explicit button click, not a multi-second freeze (the freeze was the separate, now-fixed, blocking-start-loop/hung-event-loop issue) — left as out of scope for a stabilization ticket that explicitly says not to redesign business logic or UI architecture.
- Port-reservation is a best-effort probe, not airtight against a simultaneous bind from another process in the same instant.
- LAN IP selection prefers RFC1918 private addresses but does not attempt to specifically exclude a virtual/container adapter's address if it happens to also be in a private range (e.g., a Docker/WSL/VPN virtual adapter's own private-range IP) — documented as a plausible remaining edge case on machines with such adapters active, not reproduced or confirmed here.
- The exact Windows/`ProactorEventLoop`/threaded-Tk-app interaction that caused the hang was diagnosed by controlled reproduction (with vs. without preceding GUI work) rather than traced to a specific line inside CPython/asyncio's own internals — sufficient to identify and fix it reliably, but the very last mechanistic detail (why heavy prior work specifically prevents `ProactorEventLoop`'s IOCP-based startup from ever completing, rather than merely delaying it) was not further pursued once `SelectorEventLoop` was confirmed to fully resolve it.

## RC1 Real-Laptop Server Start Hang — Targeted Debug Pass — September 2026

**Follow-up to the RC0 stabilization ticket above.** RC1 still hung on the organizer's real Windows laptop: Settings showed `Server: STARTING` for ~2 minutes with `LAN Address: —`, and the log showed literally nothing between `START requested` and the organizer's own `STOP requested` click — no port, no event loop, no uvicorn, no exception. The goal of this ticket was to find the exact stage the packaged server thread hangs at, not to guess another fix first.

### FINE-GRAINED STARTUP TRACE

`services/captain_bidding_server.py` gained a `_trace(marker, detail)` method that both logs immediately (`log_event`, flushed at once) and records `self._last_stage` for later use in a timeout error message. Every stage of `start()`, the server thread, the startup watcher, and LAN detection now emits a numbered marker: `SERVER_START_01`-`06`, `SERVER_THREAD_01`-`12` (including split `10B`/`10C`/`10D`/`10E` sub-stages for `startup()`/`main_loop()`/`shutdown()`), `WATCHER_01`-`04`, `LAN_01`-`04`. No PIN or token is ever logged (verified by an existing and a new test that exercise a real login through the trace-logged lifecycle).

### THE MANUAL EVENT-LOOP-CONTROLLED SERVE (uvicorn `run()` vs `serve()`)

RC1's fix passed a `loop=` factory string into `uvicorn.Config`; reading uvicorn's own source (`uvicorn/server.py`) showed `Server.run()` calls `asyncio.run(self.serve(...), loop_factory=...)`, which still leaves uvicorn's own `asyncio_run`/`capture_signals()` machinery in charge of exactly when and how the loop is created — an extra layer between "the fix" and "the thread," and the least-instrumentable part of the whole hang. `_run_server` was rewritten to take manual control instead: it creates `asyncio.SelectorEventLoop()` itself, calls `asyncio.set_event_loop(loop)`, constructs `uvicorn.Config`/`uvicorn.Server` **inside the thread** (not on the main thread beforehand), and calls `loop.run_until_complete(self._traced_serve(server))` — a small instance method that inlines uvicorn's internal `_serve()` (`config.load()`, `server.lifespan = config.lifespan_class(config)`, `await server.startup()`, then `await server.main_loop()`, then `await server.shutdown()`), tracing each step. `serve()`'s own `capture_signals()` wrapper is deliberately skipped: reading its source confirms it's a documented no-op off the main thread ("Signals can only be listened to from the main thread"), so bypassing it has no functional effect here. This gives full visibility into a hang that could otherwise be hiding anywhere inside `server.run()`'s own call stack.

Verified with real runtime logging (not source-reading) that the loop actually constructed is `asyncio.windows_events._WindowsSelectorEventLoop` — confirming the RC0 `SelectorEventLoop` fix is genuinely wired into the running code, in both source mode and a real frozen `.exe` (see "Frozen diagnostic" below).

### A MAJOR DISCOVERY: the hang is not exclusive to PyInstaller

Investigating this ticket's own required source/frozen comparison surfaced a reproducible hang in plain `python -m pytest` (never frozen): running the *full* `tests/test_live_auction_screen.py` file (126 tests, heavy on real `CTkToplevel` SOLD/UNSOLD dialogs) reliably hung the first test in that file to start a real `CaptainBiddingServer`, while the same test in isolation always passed in ~50-100ms. This reframes the root cause as a genuine Windows/asyncio-loop-bootstrap interaction with prior heavy Tk work in the same process — not something specific to PyInstaller packaging, contradicting RC0's working assumption. The exact CPython/Windows mechanism (why prior Tk dialog churn delays `SelectorEventLoop`'s bootstrap) was not traced further once the practical mitigation below was confirmed to work against this real, reproduced hang — a stronger validation than a synthetic unit test alone.

A related finding: the slow bootstrap is not permanently stuck — abandoning it (via a timeout) and retrying immediately can make the abandoned thread's own slow bind complete moments later and collide with the retry's bind on the same port (`SystemExit`: address already in use). The fix budgets enough time for the slow case to self-resolve before ever abandoning it, and any retry logic (in tests, and in the guidance an organizer would follow) must wait for the abandoned thread to fully finish, not retry immediately.

### BULLETPROOF STARTUP TIMEOUT

The real organizer log's core mystery — a background thread going completely silent, including never logging its own timeout — is addressed two ways:
- `_run_server`'s exception handling widened from `except Exception` to `except SystemExit` then `except BaseException`, with the exception type, message, and full traceback logged, so a `KeyboardInterrupt`/`GeneratorExit`/anything else can no longer die silently.
- A new `check_startup_timeout()` method — a cheap, lock-protected check of `time.monotonic()` against `_starting_since` — is called every poll tick from **both** Settings' `_poll_captain_bidding_startup()` and Live Auction's `_poll_captain_bidding_state()` (both Tk `after()`-driven), so the timeout no longer depends on any background thread (the watcher included) ever running again. If the budget (`_STARTUP_TIMEOUT_SECONDS`, widened from an initial 8s/10s to **20.0s** to give the rare slow-bootstrap case room to self-resolve rather than being abandoned into a retry collision) elapses, `state` becomes `FAILED` with `last_error = "Server startup timed out at <last completed stage>."` — Settings shows this directly. The app remains fully usable in manual mode while FAILED; STOP and a fresh START both work from FAILED.

### SOURCE MODE CONTROL / FROZEN DIAGNOSTIC

## First Auction Rules V2 — September 2026

**Replaces the flat 1M minimum price / flat 1M-per-slot reserve (see "PRE-M9 BUDGET RESERVE RULE" below, kept for history) with position-aware base prices and a dynamic completion reserve.** Starting budget (100M), final squad size (8, including captain), and 7 auction purchases per team are all unchanged. Second transfer window / match-result budget awards / standings / tournament FPL scoring were explicitly out of scope and were not touched.

### BASE PRICES

`models/player.py`: `GK_BASE_PRICE = 4`, `OUTFIELD_BASE_PRICE = 2` — the single source of truth, imported by `models/team.py`'s reserve formula rather than duplicated. `player_base_price(player)` returns `GK_BASE_PRICE` for a goalkeeper, `OUTFIELD_BASE_PRICE` otherwise, falling back to `player.base_price` when an organizer has set an explicit per-player override (an existing, previously-unused `Player` field — no data migration needed). A bid below a player's own base price is rejected outright, even before any budget/reserve check.

### DYNAMIC COMPLETION RESERVE

`Team.minimum_completion_cost_after_purchase(*, purchasing_gk, team_has_gk)` (`models/team.py`) computes the minimum M still needed to legally complete the squad for every slot that will remain required AFTER the purchase under consideration: if the team still needs a GK afterward (doesn't have one and isn't buying one right now), that reserve is `GK_BASE_PRICE` plus `OUTFIELD_BASE_PRICE` for every other still-needed slot; otherwise it's `OUTFIELD_BASE_PRICE` per still-needed slot. Returns `None` — a structural impossibility, not just an expensive one — when the purchase under consideration would be the team's very last roster slot while it still has no GK (that GK could then never be acquired). `Team.maximum_legal_bid(*, purchasing_gk, team_has_gk)` is `remaining_budget - reserve`, or `-1` (never a legal price) when the reserve is `None`. A team may legitimately finish the auction with 0M.

`services/auction_service.py` resolves the two booleans from a real `Player`/roster and exposes the single authoritative entry points every caller uses — nothing outside `models/team.py`/`services/auction_service.py` computes this formula itself:
- `maximum_legal_bid(team, player, players)` — the numeric ceiling.
- `team_can_bid_for_player(team, player, players)` — the full eligibility gate (roster space, the one-GK-per-team rule, the "would strand the mandatory GK" impossibility check, and whether the team can afford even `player_base_price(player)`), delegating entirely to `Team.can_buy_player`.
- `team_ineligibility_reason(team, player, players)` / `budget_reserve_violation_message(team, player, players)` — the shared human-readable explanations, reused verbatim by `process_sale`'s rejection, `services/live_bid_service.py`'s phone/desktop bid rejection, and the Live Auction desktop's pre-confirmation check, so wording can never drift between them.

Worked examples (all verified by `tests/test_budget_reserve_rule.py`, tests 1-25 numbered to match this ticket's own list):

| Team state | Buying | Reserve | Max legal bid |
|---|---|---:|---:|
| 1/8, 100M, no GK | non-GK | 4 + 5×2 = 14M | 86M |
| 1/8, 100M, no GK | GK | 6×2 = 12M | 88M |
| 5/8, 30M, has GK | non-GK | 2×2 = 4M | 26M |
| 5/8, 30M, no GK | non-GK | 4 + 1×2 = 6M | 24M |
| 5/8, 30M, no GK | GK | 2×2 = 4M | 26M |
| 7/8, 10M, final slot | either (if legal) | 0M | 10M (may finish at 0M) |
| 7/8, no GK | non-GK (final slot) | impossible | illegal at any price |

### GK RULE INTERACTION

Unchanged: exactly one GK per team, checked independently of price (`purchasing_gk and team_has_gk` is always illegal, regardless of budget). New: a team can also never legally spend its very last roster slot on a non-GK while still lacking one — this is the one genuinely new structural rejection this ticket introduces (message: "`<team>` must keep its final roster slot open for a mandatory goalkeeper.").

### BLOCKED DETECTION

`_finish_transaction`'s existing BLOCKED-state check (`any(team_can_bid_for_player(...) for player in pending for team in teams)`) required no code change — it already calls the shared eligibility gate, so it automatically inherited the new rules. ## Post-Auction Match Results + Transfer Budget Tracker — September 2026

**An independent post-auction module, deliberately never touching the first-auction transaction service.** Nothing here calls `process_sale`/`process_unsold`/`place_bid`, and nothing here mutates `Team.remaining_budget`, `roster`, or `auction_spending` — see `services/match_result_service.py`'s own module docstring for the exact isolation rationale. Player releases, refunds, a second-window transfer pool, second-window SOLD/UNSOLD, and current-tournament FPL scoring are all explicitly out of scope and were not touched.

### MATCH ENTRY FLOW

A new sidebar screen, **Match Results** (`ui/screens/match_results_screen.py`, registered in `ui/screens/SCREEN_BUILDERS` and `ui/main_window.py`'s `NAV_ITEMS` between Reports and Settings). The organizer picks two different existing tournament teams (a `CTkOptionMenu` populated from the active session's own `session.teams` — never a second hardcoded team list) and enters each team's goals; SAVE RESULT validates and records the match. A debounce flag (`_save_in_flight`) guards against a genuine rapid double-click creating two records from one logical submission; deliberately entering the *same* fixture again later is still allowed and creates a second, independent record (each match gets its own generated `id`, e.g. `match_<12 hex chars>` via `services/match_result_service.generate_match_id`), matching the ticket's explicit "repeat fixtures are legitimate, accidental double-submission is not" distinction.

### WIN/DRAW/LOSS MONETARY AWARDS

`models/match_result.py`: `WIN_AWARD_M = 4`, `DRAW_AWARD_M = 2`, `LOSS_AWARD_M = 1` — the single source of truth, never duplicated in any screen or service. `MatchResult.awards() -> dict[team_id, int]` derives both teams' awards directly from the saved score (`winner_id`/`loser_id`/`is_draw` are themselves derived properties, never separately stored fields that could disagree with the score).

### ORIGINAL AUCTION-BUDGET PRESERVATION

**No snapshot is ever captured or duplicated.** `Team.remaining_budget` is already permanently frozen the instant `Auction.status` becomes `COMPLETE` — no code path (old or new) ever mutates it again, since SOLD/UNSOLD are already rejected once complete (`_validate_current_player`) and this ticket's own match-result methods never touch it either. "First auction remaining" is therefore always just `team.remaining_budget`, read directly — not copied into a second field that could drift out of sync. A team's real completion balance is used exactly as recorded (0M, 5M, 18M, or any other valid amount) — never assumed or reset to 100M.

### CURRENT TRANSFER BUDGET FORMULA

```
current_transfer_budget = first_auction_remaining_budget + sum(valid match-money awards for that team)
```

Implemented once, in `services/match_result_service.build_team_ledger`/`TeamBudgetLedger.current_transfer_budget` — always recomputed fresh from the team's live `remaining_budget` and the *current* `match_results` list, never incremented/decremented in place. This is exactly why editing or deleting a match result can never double-count or under-count: there is no running total anywhere to fall out of sync — the next read simply recomputes from scratch.

### LEDGER DERIVATION

`TeamBudgetLedger` (`services/match_result_service.py`): `team`, `first_auction_remaining`, `entries: list[MatchAwardEntry]` (one traceable line per match this team played, with its outcome and award), `matches_played`/`wins`/`draws`/`losses`, and the two derived properties `total_match_earnings`/`current_transfer_budget`. `build_team_ledger(team, results)` filters `results` down to matches where `team.id` is `team1_id` or `team2_id` — a match referencing an unresolvable/orphaned team id simply contributes to nobody rather than raising, so one corrupt record can never break every other team's ledger. `build_all_ledgers(teams, results)` builds all four at once for the Transfer Budget Tracker / Match Money Summary sections and the Reports funding summary.

### EDITING / DELETION BEHAVIOR

`AuctionSession.update_match_result(match_id, ...)` (`services/match_result_service.update_match_result`) replaces the existing record in place (same `id`/`created_at`, new score/teams/`updated_at`) — the next ledger read reflects *only* the corrected score, never the original award plus the new one, because nothing was ever added on top of anything; the whole record was replaced. Editing a match's participating teams (not just its score) correctly reallocates: the old teams' entries disappear (they no longer match the new `team1_id`/`team2_id`) and the new teams' entries appear, verified directly (`test_22_editing_participating_teams_reallocates_awards_correctly`). `AuctionSession.delete_match_result(match_id)` (`services/match_result_service.delete_match_result`) removes the record outright; its contribution vanishes from every team's next-computed ledger automatically. Both are gated identically to `add_match_result` (below) and both go through the Match Results screen's confirmation-dialog pattern for deletion (mirroring Settings' existing "Reset App Preferences"/"Regenerate All PINs" dialogs) before committing.

### SESSION ASSOCIATION / GATING

`AuctionSession` gained `match_results: list[MatchResult]` plus `add_match_result`/`update_match_result`/`delete_match_result` methods — thin wrappers (exactly like `sell_current_player`/`mark_current_player_unsold`/`place_live_bid` already are) that call the pure `services/match_result_service.py` functions and then `self._trigger_autosave()`. All three raise `MatchResultError` (a type distinct from `AuctionTransactionError` — a genuinely separate subsystem) unless `session.auction.status == AuctionStatus.COMPLETE` — enforced at this layer, not just by disabling the UI, so match-money accounting can never be recorded against an IN_PROGRESS or BLOCKED auction (a BLOCKED auction is explicitly never treated as a completed one) even if a caller bypasses the screen.

### COMPLETED LIVE SESSION RECOVERY

**No new read-only mode needed to be built** — inspecting `ui/screens/live_auction_screen.py`'s existing `_render()` dispatch (`not_started` → launcher, `is_blocked` → blocked view, `is_complete` → `_build_complete_view()`, else → in-progress view) showed the Milestone-9 session launcher's existing "Resume" button (`_on_resume_clicked` → `persistence_service.load_session` → `session.adopt(restored)` → re-render) already reopens a COMPLETE LIVE (or MOCK) save directly into `_build_complete_view()`, which was already fully read-only (final team budgets only — no SOLD/UNSOLD buttons, no team-selection, no bid controls) before this ticket touched anything. Resuming a COMPLETE session was verified directly (`test_34_completed_live_reopens_in_post_auction_mode`) to: leave `auction.status` at `COMPLETE`, never restart or replay anything, and immediately accept new match results. `NOT_STARTED`→`IN_PROGRESS` protection (a MOCK can never overwrite the LIVE slot; starting a new LIVE archives, never deletes, the existing one) is completely unmodified.

### MOCK/LIVE ISOLATION

`match_results` lives on the same per-session snapshot as `players`/`teams`/`auction` — a MOCK session's match results are written only to its own `saves/mocks/<id>.json`, a LIVE session's only to `saves/live/live_active.json`, via the exact same `session_save_path` mapping every other Milestone-9 field already used (mode never changes after a session is created). Verified directly that two sessions of different modes never see each other's match results after independent save/reload (`test_37_mock_and_live_match_results_remain_isolated`).

## Key implementation decisions

- Money is stored as integer millions (`14` means 14M) to avoid floating-point currency errors.
- Rosters store canonical player IDs; the captain is always the first initial member.
- Enums constrain player position, player auction status, and overall auction status.
- `Team.add_purchased_player()` protects budget, squad size, and duplicate membership at the model layer.
- Queue creation lives in `services/randomization_service.py`, not in the `Auction` model or any future GUI callback; the model only stores and advances state. Bidding, selling, marking unsold, and persistence still belong to services in a later approved milestone.
- Tournament-specific counts, budgets, squad limits, position colors, and increments are centralized in `data/settings.json`.
- Branding is stored as configuration (`app_name`, `branding_name`, `header_title`, `logo_path`, and `theme_name`) so a later logo or identity change does not require rewriting UI components.
- `services/config_service.py` is the single place that reads `data/settings.json` for branding/position-color values; `ui/theme.py` only holds pure-presentation constants (hex colors, fonts, window sizes) that are not tournament data.
- The UI layer (`ui/`) only calls into `models/` and `services/`; it never contains auction, roster, or persistence logic itself.
- `services/player_service.py` owns player/team loading, search/filter, and setup validation; `ui/screens/players_setup_screen.py` only renders that data — it never parses JSON or reimplements filtering itself.
- `MainWindow` routes by name through `ui/screens/SCREEN_BUILDERS`, a small dict from nav label to screen-builder function, so adding each future real screen means adding one dict entry rather than growing an `if/elif` chain in `MainWindow`.
- `services/team_service.py` owns roster-to-`Player` resolution and derived team stats (`TeamSummary`); it reuses `player_service.load_players()`/`load_teams()` rather than re-reading JSON itself, and never writes back — Live Auction's SOLD/UNSOLD service will be the first thing allowed to mutate `Team` state, in a later milestone.
- Shared, non-screen-specific widgets (colored pill badges, position badges) live in `ui/widgets.py` so `players_setup_screen.py` and `teams_screen.py` (and future screens) render them identically instead of each maintaining its own copy.
- `services/auction_service.py` is the only code allowed to mutate `Team`/`Player`/`Auction` state together; it validates everything before mutating anything (rather than mutating-then-rolling-back), so a rejected transaction is guaranteed to leave every object unchanged with no special-case cleanup code needed.
- `Player.auction_eligible` and `Player.auction_status` are deliberately different things: `auction_eligible` is a fixed category flag decided once (which 28 players were in the original pool), while `auction_status` is the live field (`AVAILABLE` → `SOLD`/`UNSOLD`) that the transaction service updates. Nothing after Milestone 3 changes `auction_eligible`.
- `AuctionSession` (Milestone 8) is the one place allowed to own the "current running auction" — `MainWindow` creates it once and hands the same instance to every screen; no screen loads its own copy of an in-progress auction, which is what makes navigation-without-reshuffling and Teams' live-state view both work for free rather than needing special-case syncing code.
- `AuctionSession.start()` being a no-op when already started (rather than the UI simply hiding the START AUCTION button) means the "never re-randomize" guarantee holds even if a future bug calls it twice — the invariant lives in the service, not in UI button visibility.
- Shared image loading (`ui/widgets.load_image_safely`) is used for both the branding logo (Milestone 4) and player photos (Milestone 8) — one implementation of "load an image, resize preserving aspect ratio, return None instead of raising on any failure," reused rather than duplicated.
- SOLD is the single permanent outcome (Milestone 8.1); UNSOLD is a transient "try again next round" result, not a rejection. `sold_player_ids` (permanent) and `resolved_player_ids` (any history entry, still available but no longer used for the "already done" check) are deliberately two different functions rather than one function whose meaning changed — so any other caller relying on the old "any history entry" semantics doesn't silently break.
- `Auction.round_number`/`start_new_round()` extend the model minimally (same pattern as Milestone 3's `is_initialized`/`advance()`) rather than introducing a second queue/history representation for rounds — a round is still just "the current contents of `queue`", replaced wholesale when a round transitions.
- `AuctionStatus.BLOCKED` is a real, renderable, terminal-for-now state (like `COMPLETE`), not an exception — because the transaction that revealed the blocked condition was itself perfectly valid and already succeeded, only what happens *next* is impossible, so raising would have been the wrong signal.
- `team_can_bid_for_player` deliberately ignores budget (only roster space + the GK rule) since it's used before a price is known (UI eligibility, blocked-state detection); `process_sale` remains the sole source of truth for a specific transaction attempt, including budget.
- `services/live_bid_service.py` (September 2026) is the one place allowed to write `Auction.current_bid`/`leading_team_id`, guarded by a single lock so a bid's validate-then-mutate sequence is atomic; `services/auction_service.py` only ever clears those two fields (on advancement) and never sets them, keeping "who is allowed to set the live bid" and "who is allowed to finalize a sale" as two clearly separate authorities even though both ultimately live in `services/`.
- `services/captain_auth_service.py` (September 2026, Phase 2) is deliberately independent of `AuctionSession`/`Auction` — *which team a bid is for* (identity/PIN authentication) and *whether that bid is legal* (`live_bid_service`) are two separate concerns; the HTTP layer (`captain_bidding_server.py`) is the only code that combines them, by resolving a token to a team id and then handing that id to `AuctionSession.place_live_bid` exactly as a desktop click would.

## Known issues / intentional gaps

- Ratings were refreshed and organizer-approved in September 2026 (see "Player Data Refresh — September 2026"), but the organizer may still revise player data before tournament day.
- No sidebar route still shows Milestone 4 placeholder text — Players & Setup, Teams, Live Auction, Auction History, Reports, and (September 2026) Settings all have real screens. Player/team database editing/management remains explicitly deferred; captain phone bidding now supports mixed-mode, PIN-authenticated bidding for 0-4 teams simultaneously (Phase 2, September 2026 — see "Captain Phone Bidding — Phase 2 — September 2026").
- **Captain Phone Bidding was never tested against a real physical phone in this development environment** (sandboxed, no phone on the same network), across both Phase 1 and Phase 2 — it was instead verified via full protocol-level simulations against a real bound HTTP socket. The organizer should follow the manual test steps in `README.md`'s "Captain Phone Bidding — Local Test" and "Four-Captain Setup" sections with real phones before relying on this for tournament day. Connected-status is heartbeat/polling-based (a captain seen within the last 5 seconds), not a guaranteed-exact signal under every possible network condition.
- **Captain PINs are a local-tournament-appropriate security level, not enterprise-grade.** A 4-digit PIN over an open Wi-Fi network protects against an idle bystander casually bidding on someone else's behalf, and the login-throttling described in "Captain Phone Bidding — Phase 2" rules out a trivial brute force — but this is explicitly not designed to resist a determined, technically capable attacker on the same network. Acceptable for a one-day, trusted-venue tournament; would need real hardening (HTTPS, longer credentials, per-device pairing) for any higher-stakes use.
- Captain auth session tokens are in-memory only and are lost on a full application restart (not on a Captain Bidding server STOP/START, which the same `CaptainAuthService` instance survives) — a captain simply re-enters their still-valid PIN in that case. This is a deliberate simplicity/security tradeoff, not an oversight (see "AUTH SESSION DESIGN" in "Captain Phone Bidding — Phase 2 — September 2026").
- QR-code joining, WebSocket push, and a richer tournament-day offline/reconnect UI were all deliberately deferred past Phase 2 — see that section's own "Phase 3 and beyond" note.
- **The RC1 Windows packaged build (see "Windows Packaging — RC0 — September 2026" and "Windows RC0 Packaged-Runtime Stabilization — September 2026") is a test build to validate packaging, not the final tournament release** — no `.ico` icon, no code signing, and it has only been built and run on the same machine/environment it was developed in (not yet verified on a separate "clean" Windows machine with no Python installed). RC0 had a real, confirmed packaged-only bug (the captain-bidding server could hang indefinitely after other GUI work — see the stabilization section); RC1 fixes it and was re-verified against the same reproduction, but build and test RC1 itself on the actual tournament laptop before relying on it on tournament day.
- Auction History and Reports are both entirely read-only by design (see "Auction History — September 2026" and "Reports — September 2026"): no undo, edit, delete, or reassignment of a past transaction exists on either screen. A future organizer recovery workflow (e.g. undoing a mis-entered sale) remains explicitly out of scope, same as the existing BLOCKED-state recovery gap noted above.
- Reports has no PDF/CSV export yet (explicitly deferred) — its data is structured as plain dataclasses (`services/report_service.py`) specifically so an export feature could be added later without restructuring the underlying calculations.
- Players & Setup remains fully read-only by design. Teams remains read-only for manual edits but now reflects live auction purchases when a session is active. Live Auction is the only screen that mutates state, and only via the Milestone 7 transaction service — never directly.
- **Canonical `data/players.json`/`data/teams.json` remain entirely read-only reference data** — nothing, including Milestone 9's persistence layer, ever writes back to them; a running auction's mutable state now lives in `saves/` instead (see "Milestone 9 — Persistence / Autosave / Recovery" below). Closing the application no longer loses a running auction — it autosaves after every state-changing action and can be resumed exactly via the Live Auction screen's session launcher.
- The budget-reserve rule's "team can't legally afford even the minimum price" case (`team_can_bid_for_player` returning `False` purely on budget grounds) should, per the ticket, "normally only arise from invalid/synthetic state" in a properly run tournament, since the rule is enforced continuously at every sale — it's handled safely (contributes to BLOCKED-state detection like any other ineligibility reason) but isn't expected to occur in a real auction where the organizer never bypasses the app.
- No live bidding between teams — one final price is entered per sale by the organizer (with optional +1M/+2M/+5M quick-adjust buttons on the price field itself, not a bid ladder between teams).
- A poorly-managed auction (an organizer who buys GKs/fills rosters without thinking ahead) can genuinely reach a BLOCKED state — this is correct, intentional behavior (see Milestone 8.1), not a bug, but it means there is currently no way to *recover* from a blocked auction within the app (no undo, no manual reassignment) short of restarting the whole session. A recovery/undo workflow remains out of scope, including after Milestone 9 — persistence lets you resume a BLOCKED session exactly as it was, but doesn't add a way to un-block it.
- Milestone 9 has no schema migration: if a save file's `schema_version` doesn't exactly match the app's current `persistence_service.SCHEMA_VERSION`, it's rejected with a clear error rather than upgraded — acceptable for a single-developer, single-deployment tool today, but a future format change would need real migration logic.
- No UI browses archived LIVE sessions (`saves/live/live_archived_*.json`) — they're preserved on disk (never deleted) for manual inspection/backup, but only the current `live_active.json` is surfaced in the session launcher. Only the current MOCK/LIVE saves are listed; nothing prunes old mocks automatically, so a very long test/practice history would need manual cleanup (deleting a mock from the launcher, or the file directly).
- Persistence assumes a single application process at a time — there's no file locking, so two instances of the app pointed at the same `saves/` directory could race on the same save file. Not a concern for the tournament's actual single-organizer, single-laptop usage.
- Windows packaging (PyInstaller or similar) is still not implemented, as instructed — `saves/`, like `data/` and `assets/`, resolves relative to the source tree's `ROOT_DIR` today; a packaged build would need its own writable install-relative (or user-profile) location, which is deliberately out of scope for this milestone.
- The GK-coverage setup check (`validate_setup`) is a static sanity check using `>=`, not a guarantee: it does not simulate the auction, so it cannot promise a *specific* auction run won't still end up BLOCKED (e.g. from filling teams up before they get a GK) — only that there are structurally enough GKs for it to be *possible*. The runtime BLOCKED-state detection is what actually catches a bad outcome.
- Player photos: all 32 canonical players now have a real photo asset under `assets/players/` with a populated `photo_path` (see "Player Photo Integration — September 2026"). The safe-loading/fallback path (missing file, corrupt file, no `photo_path`) remains fully exercised for the cases it still needs to cover — team-purchased-player edge cases, a future roster edit, or a photo file later going missing.
- Player Cards' detail view can require scrolling to see every field on a tall or DPI-scaled display, since it shares the same `load_cover_fit_image`-based photo sizing as every other screen — intentional (a `CTkScrollableFrame` wraps it precisely so nothing clips), not a defect; see "Player Cards + Last-Season FPL — September 2026" for why an in-page panel was used instead of a dialog.
- Last-season FPL points are a display-only statistic sourced from one organizer-supplied result sheet — they play no role in any auction rule (budget, GK, re-auction, sorting a real auction queue) and are not validated against any external FPL data source; a future correction would be another manual `data/players.json` edit, the same as a rating correction.
- Cross-model operations (for example updating Player and Team atomically) are handled by `services/auction_service.py` for the SOLD/UNSOLD case specifically; no other cross-model operation exists yet.
- Base prices are not assigned because the specification provides examples, not final values. The transaction service accepts a final sale price supplied directly by the caller rather than deriving one from a base price or live bidding.
- Team assets/logos are not added; the official branding logo is present. Team cards (Teams screen and Live Auction's team-status row) use plain text/name only, as instructed.
- `Auction.advance()` itself still only moves the queue pointer and does not touch `status`/history — `services/auction_service.py` is what calls `advance()`, writes `AuctionHistoryEntry` records, and syncs `Auction.status` to `COMPLETE`, exactly once per successful transaction.
- GUI-creation tests (`tests/test_ui_shell.py`, `tests/test_players_setup_screen.py`, `tests/test_teams_screen.py`, `tests/test_live_auction_screen.py`) only run when a real display/Tk backend is available; they skip (do not fail) in a headless environment. Most share one session-scoped hidden Tk root (`tests/conftest.py`) to reduce flaky TclError teardown timing from repeatedly creating/destroying CTk() roots in one process — the two tests that build a full `MainWindow` (in `test_ui_shell.py` and `test_live_auction_screen.py`) each still create their own separate root (a screen frame can't substitute for the app's own top-level window) and occasionally skip for the same underlying reason; both pass reliably in isolation.
